# Task 7 — checked answers and failed turns

The daemon hand-in route dispatches Aristotle attempts to labmemory.Answers. The authenticated runtime owner must be the run requester. The requester’s membership is share-locked, and Read verifies the transaction identity against that member. Terminal replay is accepted only for an already recorded answer to this run. A plain gap still requires a current member. The run/attempt lock and unique outcome index keep concurrent and repeated submissions from duplicating a message or its event.

The answer is validated against one PostgreSQL serializable snapshot. Other hand-in kinds retain their existing transaction isolation. Discovery of an Aristotle run re-enters under that isolation and rechecks workspace, runtime ownership, attempt, and run locks before the callback. Bounded retries (four attempts for PostgreSQL 40001) discard staged effects before trying again. Ordering a simultaneous fact edit before or after a hand-in is permitted; an edit committed before the hand-in snapshot must be visible. Citation validity is checked at acceptance; this task does not revalidate historical answers on later display.

Every batched read comes from the server’s own lab_read rows for this run. Logged direct reads, search hits, link sources and followed edges are usable under the existing tool contract; a search hit is logged only after its live requester read. The result stores statement kind/text and server-resolved ref/title pairs, plus evidence ref/title/via. Exact repeated log entries are deduplicated. Inaccessible targets are omitted and cannot serve as cites. A formerly visible edge source is redacted if it is no longer visible. An active, checked lesson is usable only if every supporting fact opens and its pinned version still matches. The read-log policies now also protect other members’ private run trails against peer reads or writes; the log has no app update/delete policy. The recorder is scoped to a running Aristotle run, its workspace, current requester membership and requester-owned chat; its qualified relation names are independent of temporary tables. There is no new migration above 0052.

The failed run’s durable settlement writes one failure message using allowlisted, plain language derived from the actual stored reason. Neither daemon error text nor the private question is used in the message or the event; the event has only message/chat/owner identifiers. Successful or cancelled Aristotle settlements do not add failure messages. A removed requester gets no new message. The actual HTTP daemon test uses the existing two re-ask limit and checks same-session resume and three posts before failure. No Codex adapter changes; Codex remains refused at enqueue and launch.

## Shutdown and delivery limits

The normal daemon test originally stopped its daemon as soon as status changed. That legitimately cancelled an in-flight settlement, and a fresh recovery pass could not steal its live five-minute lease. The normal test now lets delivery finish before teardown. A **separate interrupted-delivery test** calls the real Fail path, cancels its request only after both terminal status and delivery claim commit, observes the pending row and active lease, and constructs a fresh service with the same database. Its recovery skips the active lease. After advancing only that lease's expiry in the fixture, two recovery passes yield one failure message and a delivered receipt. The production server attempts recovery at startup and in its sweep; recovery is eventual while a server runs and the requester still has access, not synchronous with the failed status. No real machine crash, five-minute wall-clock wait, or signed-in CLI/provider call was used.

The Task 7 tests exercise synthetic fixtures; they do not cover floating-window UI, live paid models, human assessment of claim semantics, or the separate Codex managed-config containment gap. The entire repository test suite was not run.
