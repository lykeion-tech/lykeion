## What the architecture actually separates

Multica already separates a Go control server from TypeScript web/Electron shells and shared client packages. Its declared client dependency direction is views → core + UI, while core and UI remain independent. The useful lesson is platform separation and shared domain behavior, not a requirement to reuse package names or module boundaries. See [AGENTS.md](https://github.com/multica-ai/multica/blob/b115ec80f1748d8d2766481706b0ecb830389286/AGENTS.md#L11), [server/go.mod](https://github.com/multica-ai/multica/blob/b115ec80f1748d8d2766481706b0ecb830389286/server/go.mod), [apps/desktop/package.json](https://github.com/multica-ai/multica/blob/b115ec80f1748d8d2766481706b0ecb830389286/apps/desktop/package.json).

Its deeper separation is **issue ≠ run ≠ runtime ≠ agent**. An issue carries the durable intent; a run is an attempt to do work; a runtime is execution capacity; an agent is a configured actor. Scientific work needs this separation plus durable claims, protocols, observations and validation judgments. Those scientific entities cannot be represented reliably by comments alone.

## Reliability mechanisms worth specifying independently

1. **Durable dispatch and idempotent settlement.** The server and worker must agree on task/attempt identity. Terminal callback replay is normal, and duplicate delivery must not trigger duplicate evidence acceptance or spend settlement. Multica's task completion compare-and-swap and local terminal outbox are direct examples of this need.
2. **Leases are operational, not epistemic.** Database time, heartbeat freshness, token-fenced takeover and bounded recovery determine who may execute. They say nothing about whether a scientific result is valid. A recovered worker cannot overwrite newer result acceptance.
3. **Version-pinned handoffs.** A model receiving a compact summary still needs stable artifact references. Preserve the complete canonical record outside the prompt, including facts omitted by context limits. Every downstream result points back to the exact accepted inputs.
4. **Two different retry loops.** Re-running after a transport/process failure is an infrastructure retry. Changing the hypothesis, parameters, metric or protocol is a new scientific revision/trial and must be counted and reviewed as such. Blind retry-until-significant is not a reliability feature.
5. **Independent retention.** Completed process output, failed attempts, rejected validation and null findings remain inspectable. Keeping only the winning experiment introduces selection bias into the system itself.
6. **Compatibility across installed clients and workers.** The Go server controls allowed transitions; TypeScript projects them; Python produces typed scientific results. A stale desktop client cannot bypass a new evidence requirement.

## Where Multica's assumptions must change

| Question | Reference behavior | Scientific replacement to discuss |
|---|---|---|
| What constitutes work? | Deliver the issue's requested outcome, often code/PR-related. | Reduce uncertainty about an explicit question, or produce a defined artifact needed for that reduction. |
| What constitutes completion? | Run terminates; issue separately advances to review/done. | Run terminates → outputs checked → evidence evaluated → stage gate satisfied. Null results can be successful research. |
| Who coordinates? | Assignee or squad leader responds to triggers and promotes children. | Go enforces durable dependencies and gates; planning agents propose revisions within policy/budget. |
| Who owns a result? | Workspace/agent/runtime/originator metadata and branch/session ownership. | Campaign authorization, executor provenance and independent validator identity remain distinct. |
| What is review? | Human/agent review of delivered work and linked code revisions. | Technical reproducibility, statistical/methodological validity and claim-to-evidence support each require explicit checks. |
| Does closing a child satisfy a dependency? | Stage barrier can close with done or cancelled children. | Only accepted evidence satisfies a required scientific dependency. Waiving a requirement is a recorded protocol change. |
| Does autonomy remove stopping? | Agents continue when triggered and eligible. | Autonomy includes stopping on insufficient evidence, exhausted budget, irreproducibility or unresolvable ambiguity. |

## Dependency inventory and proposed separation

Observed upstream dependencies are examples, not Lykeion requirements. The Go manifest includes Chi HTTP, pgx/PostgreSQL, Gorilla WebSocket, Redis, Prometheus, AWS SDK storage, Cobra CLI and provider/integration libraries. The desktop package includes Electron, React, React Router, TanStack Query and shared TypeScript packages. Upstream uses sqlc-generated persistence code and a pnpm workspace; these choices do not bind Lykeion.

A defensible division for the requested stack is:

- **TypeScript web/desktop:** research board, evidence inspection, protocol/version diffs, run telemetry, controls and reproducibility views. Share research behavior and components; isolate native filesystem, runtime enrollment and updates.
- **Go control backend:** identity, permissions, durable state machine, scheduling/leases, resource/budget reservations, event delivery, artifact references, immutable decision records and gate enforcement.
- **Python scientific service/workers:** literature/source adapters where useful, computational protocol execution, domain-library integrations, statistics, verification routines and artifact production. Long tasks need asynchronous job/attempt contracts, cancellation and durable outputs; an HTTP request alone is not their lifecycle.
- **Persistent stores:** relational state/audit metadata plus content-addressed or checksum-verified scientific artifacts. A data/compute manifest must record inputs, code revision, environment, seeds, execution parameters, outputs and validation links.

These are proposed responsibility boundaries, not approved services or repositories. Avoid mirroring Multica's module graph mechanically, especially its broad task service.

## Grounding-specific implications for the current discussion

Grounding should leave a versioned problem/evidence package rather than merely a prose literature summary. Multica contributes useful transport mechanisms—durable tasks, structured handoffs, source-linked activity, reliable retries—but no inspected mechanism establishes that a research question is well-posed or adequately grounded.

Candidate Grounding outputs for discussion: the question and scope; known findings with resolvable source references; disagreements and missing evidence; operational definitions; available computational data/resources; and candidate criteria by which later results could address the question. Which of these is mandatory is a scientific-model decision still open with the user.

The backend distinction is useful immediately: an agent can **propose** a Grounding package; a schema/source checker can verify required fields and references; a methodological reviewer can assess adequacy; the Go gate records acceptance or requests revision against the exact package version. These checks establish traceability and minimum adequacy, not proof that the literature is exhaustive or the proposed claim is true.
